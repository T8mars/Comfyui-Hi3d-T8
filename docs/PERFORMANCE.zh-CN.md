## v0.5.1 权重搬运与阶段预读

TRELLIS.2 的按需加载增加双缓冲异步显存搬运。每次使用两个 16 MiB 锁页缓冲，交替执行 CPU 暂存与独立 CUDA stream 拷贝；复用缓冲前等待对应事件，全部拷贝完成后才报告显存权重就绪。保持原始数据类型、计算缓冲与随机状态。小模型、非连续或自定义张量、额外类型转换及内存不足时使用标准搬运；锁页分配失败在修改模型前回退，已开始的 CUDA 执行错误继续向上传递。按真实完成的字节显示进度，并记录 CPU 暂存与总搬运耗时。

阶段预读在当前模型输出保存后启动，可与下一阶段的准备／UV 工作重叠。只读取所选引擎和分辨率的权重，使用一个 8 MiB 缓冲，按可用内存选择最多 8 GiB 的文件；开始实际权重加载时，在下一缓冲边界停止后台读取。它只预热系统文件缓存，模型仍按需构造和上传；停止、失败和任务结束会关闭读取线程，报告保留预读量与交接原因。

真实 1.3B 检查点的 640 个状态张量逐个完全一致，CPU／CUDA 随机状态未改变。标准上传三次为 3.801／1.484／1.825 秒，分块上传为 0.923／0.887／1.382 秒；首个标准样例包含较冷的读取，不据此承诺固定倍速。额外真实 CUDA 验证覆盖混合精度、整数／布尔与非持久缓冲、共享参数、非连续张量回退、锁页失败，以及拷贝排队后异常的缓冲生命周期。

仅影响独立工作台的 TRELLIS.2 加载；ComfyUI 独立 Hi3D 节点保持现有模型范围。需要诊断对照时，可在启动环境设置 `HI3D_WEIGHT_TRANSFER=off` 或 `HI3D_STAGE_PREFETCH=off`。原理参考 [PyTorch 锁页／异步拷贝说明](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html)。


同参数百万面/4K完整任务按关闭/开启/开启/关闭交替，耗时为 **201.719/158.000/160.969/163.422秒**，原始几何字节一致。解释器保持，系统/UV缓存未清空，GPU网格整理有非确定性，不作通用倍速承诺。另固定同一份整理后网格和形状编码缓存，确认几何、UV、法线及两张4K贴图逐像素完全一致；第二次固定网格任务命中缓存，不把其耗时当作单纯上传速度对照。四份GLB通过标准校验，两份完整模型通过CPU/HDR三视角渲染。[v0.5.1证据](../validation/v051-loading.json)。

## v0.5.0 实现与验证

默认「阶段释放，保持运行时就绪」仅保留解释器，不保留模型权重；「常驻模型内存」另启用受限 CPU 缓存，「完成后退出」则结束运行时。释放、取消、异常和关闭工作台均保留所属进程清理；省显存选项单独控制 GPU 卸载。

权重预读最多一个顺序任务、一个 8 MiB 缓冲，受可用内存保护。CPU 参数构造、真实文件读取量和显存搬运分别报告。选择性 meta 参数赋值保持原始混合精度、实际计算的 RoPE 缓冲及随机状态，不支持时回退官方加载器。真实 1.3B 权重对照的 641 个状态张量和缓冲完全一致，官方／优化 CPU 加载为 23.695／0.141 秒；官方先运行、存在系统缓存先后差异，不代表整套推理的固定倍数。固定来源源码未变化时也复用文件身份绑定的哈希校验。

GPU 体素化是独立的 `hi3d_voxel_cuda` 组件，基于[固定版本社区 GPU FDG 实现](https://github.com/quantaji/o-voxel-gpu/tree/e477c69457c650dc680c02c2a1fb2ca58d3429ad)。本项目使用两个有流顺序的占用写入阶段修复 warp 自旋等待，并采用严格 FMA 设置；不替换 `o_voxel`。固定 Windows CPython 3.12／Torch 2.8.0+cu128 轮子包含 8.6、8.9、12.0+PTX，其他架构使用 CPU。安装前校验大小和 SHA256，再运行真实 CPU/GPU 基础校准，不解析或升级依赖。自动模式检查空闲显存，可恢复的显存不足和数值校验失败回退 CPU；不掩盖不安全的 CUDA 错误。

五组网格测试（含 971,356 面、512／1024）占用体素坐标及相交标记完全一致。QEF 顶点浮点数不逐位相同：1024 的 RMS 约 4.52e-5，最大差异一个体素宽度。包括传输和规范排序的 CPU／GPU 体素化为 56.221／7.730 秒，其中原生调用部分单独为 0.393 秒；不能混用计时范围，也不能当作完整贴图耗时。每个进程会用 64 格立方体校准：整数结构完全一致，浮点 RMS 和离群值有独立上限。

表面编码缓存保留稀疏特征及必需的拓扑／上采样映射。键绑定归一化网格、分辨率、模型身份、源码、运行时及实际 CPU/GPU 后端。文件不使用 pickle，核对数组哈希及 ZIP CRC；单条上限 1 GiB、总量 4 GiB，并保留磁盘空间。无效／缺失条目重新计算，不缓存生成的贴图。CPU、GPU 结果使用不同键。

PBR 烘焙保留原采样、量化、Telea 半径（3/1/1/1）、法线和 UV 变换，只并行四路独立补边，受内存保护，失败时等待所有线程退出。真实 4K 金样与官方串行烘焙对照：材质像素、顶点、面、UV、法线完全一致；读取完整稀疏拓扑缓存后重跑的材质像素也完全一致。串行整段烘焙和并行补边子段计时范围不同，不据此计算提速倍数。

同图、百万面预算、几何 512／材质 1024、12+12 步／4K 的完整流程墙钟 **215.250 秒**，流水线报告 201.82 秒，原始几何与 v0.4.8 字节一致。同网格再次仅贴图为 **117.782 秒**，复用同一运行时并命中表面编码缓存；默认策略下常驻模型条目为零。两项流程范围不同。此前 v0.4.8 完整案例为 406.063 秒，磁盘缓存及系统负载不同，不承诺固定倍数。

在「模型与环境 → 可选 GPU 体素化加速」安装，或运行 `runtime/python.exe tools/setup_pipeline_runtime.py --runtime runtime-pipeline --voxel-only`。代码更新保留环境和权重；缺失／过期组件时仍可用 CPU，不影响模型就绪计数。终端和页面均显示真实读取量与阶段进度。GitHub 附件继续只含代码。

v0.4.5 调整独立工作台的 UV 准备、进度显示，并提供可选的 TRELLIS.2 注意力加速。ComfyUI 节点及画布工作流继续只做 Hi3D 几何精修，不新增工作台的其他引擎。GitHub 源码、节点、代码更新和启动器附件均不含 Python 或模型权重，完整整合包由 T8star 另行提供。

## GPU 占用低时，任务可能在做什么

本次慢任务不能据此判断为“模型渲染没有使用显卡”。其几何阶段用 CUDA 完成，耗时 158.684 秒，输出 973,968 面。旧 UV 路径可能先完成一次原生展开，再因顶点／法线对应检查未通过，把整张网格交给 CPU xatlas 重做。原任务在 UV 事件后至少等待 1,381.888 秒才取消；这属于中断等待记录，不能当作一次成功展开的耗时。见[验证记录](../VALIDATION.md)。

运行时导入、权重读取、CPU 参数化／排布和导出阶段，都可能让 GPU 暂时闲置。本次 Windows 诊断还发现了加载 DLL、权重时的 E 盘 PageIn 等待，属于磁盘及内存读页开销。注意力模式或 INT8 模型无法单独解决这类等待。比较速度时应分别记录加载、采样、UV 和导出的时间。

TRELLIS 网格编码也先使用官方 `o_voxel` 的 CPU 体素化路径。工作台将其显示为 CPU 准备，仅在 shape encoder 真正开始 forward 时才切换为 CUDA 编码。这段 GPU 占用低是预期行为，不会因为后续编码使用 CUDA，就把前面的准备也标成 CUDA。

存储快照将 E: 对应到磁盘／SCSI 端口 1，记录瞬时队列长度 28，并发现同日较早的 `stornvme` 事件 129 对 `RaidPort1` 发出重置。另一次两秒采样中，E 盘 1,782 次读取的平均延迟为 14.808 ms；C:/D: 同期只有一次读取（1.391 ms），不能作为公平硬件对比，也不能据此认定硬盘损坏或确定某个驱动原因。开发机原始记录：`data/v045-storage-evidence.json`、`data/v045-read-latency.json`。

## 网页与启动窗口显示的进度

两处同步显示真实的阶段／环节事件、已处理数量、阶段耗时、距上次有效进展时间；仅在阶段明确报告时显示 CPU 或 CUDA。TRELLIS 采样、模型加载及 UV 准备各自提供计数。加载计数表示已载入的模型数量，不是已读取权重字节的百分比。

采样兼容 `step/steps` 和 `step/num_inference_steps`。第几次采样对应真实的 sampler 调用，不虚构总轮数。已知总量的环节显示局部进度条；只有迭代／合并数量、没有总量时，只显示数量和说明，不编造百分比或剩余时间。加载期间没有新事件，可能使“距上次有效进展”继续增长，不能仅凭这个时间判断任务已卡死。

stderr 的进度显示可能把 `HI3D_EVENT` JSON 挤到回车显示行中间。共用解析器可从前后显示文字中恢复事件，拒绝坏 JSON／非有限数值，并保留原始阶段日志；管道补充所属阶段后只转发一次规范事件。高频回调对终端输出与磁盘写入节流，API 内存状态保留最新已观察进度。

## UV 准备与缓存

默认顺序为 **CuMesh 原生 → 社区 GPU PEC → 有界 CPU 分区**。首选路径复用 CuMesh 的 GPU 聚类与 xatlas 参数化，验证源对应关系并局部修复 UV 错误，普通路径可省去额外 Comfy／LLVM 模块冷加载。固定版本的 ComfyUI 社区路径作为备选，保留源索引，不自动焊接顶点。安全回退按源拓扑分区进行 CPU Atlas，避免把整张大网格再次送入无界展开。结构性 UV 错误保持可见，不会为了完成任务接受无效结果。

检查覆盖源面、绕序、位置、逐角着色法线、UV 有限值和范围、零面积 UV 三角形，以及完全重复／镜像复用的 UV 三角面。局部修复可以分离受影响的 UV 角点，不对源几何减面。这些检查不等于穷尽检测所有任意局部重叠。

已验证的 UV 存入 `data/uv-cache`，缓存身份包含几何、法线、绕序、贴图尺寸、间距、后端及算法／源码哈希。读取时重新校验内容，损坏或不兼容时重新展开。缓存只存 UV 与索引，不存生成的材质像素；再次贴图仍需运行贴图模型。已有可用图集可以直接跳过展开。

原问题的 973,968 面网格，现已通过两条 UV 路径及缓存回读。两者均保留全部 973,926 个有效源面，仅排除同样的 42 个精确零面积面，没有对有效几何减面。

| 显式 UV 后端 | 首次实测展开 | 已验证缓存回读 | 局部修复 UV 面数 |
|---|---:|---:|---:|
| CuMesh 原生 | 65.155 秒 | 1.275 秒 | 108 |
| 社区 GPU PEC | 162.418 秒 | 1.437 秒 | 2,543 |

这些是 UV 准备耗时，不是贴图生成或完整任务耗时。社区运行包含约 54 秒依赖冷读、18 秒 Numba 首次 JIT，不能由此概括为 CuMesh 算法普遍快 2.5 倍。此输入的原生路径还需要更少局部修复，因此选作默认，但不构成普遍质量排名。原生修复的 108 面中，107 面涉及重复 UV、97 面涉及最小高度调整，分类相互重叠，不能相加；内部图集边长扩展至 4,112。社区修复的 2,543 面均来自源网格同位置反绕序的重合面实例，含 14 面最小高度调整，该修复报告没有无关表面的 UV 冲突。原始证据：`data/uv-verified-v045/results.json` 及各后端事件／修复记录。

两条路径各自的首次与缓存输出，共四份实际 GLB，也已通过 `load_texture_input` 重载审核：源位置在 float32 精度逐顶点完全一致，法线通过 `rtol=0, atol=2e-6` 检查，973,926 个有向源面实例全部保留，落盘 UV 通过零面积／完全重复检查。这证明 UV／几何的导出重载，不代表已生成 PBR 或材质效果合格。回执：`data/uv-verified-v045/glb-roundtrip.json`。

**新建 TRELLIS.2 几何**的表面整理提供 10 万、30 万、100 万面预算，默认保持 100 万。原始生成几何另存供对比。较低预算可减少后续网格处理，但可能损失细节。**已有模型贴图不使用该面数预算，不会对上传模型减面。**

## TRELLIS.2 注意力选项

| 选项 | 行为 |
|---|---|
| `auto`，默认 | 实测原生 packed FlashAttention CUDA 内核；不可用时明确报告并使用融合 SDPA |
| `flash_attn` | 必须通过原生探针；固定扩展不可用时明确报错 |
| `sdpa` | 使用显式的 PyTorch 融合 SDPA 兼容路径 |

该选项只作用于 TRELLIS.2 建模／贴图，Hi3D 的 `attention` 设置保持独立。TRELLIS 的 dense attention 仍使用 SDPA；原生选项加速满足条件的 sparse packed 调用。不符合原生数据类型或 head dimension 的调用保留原精度并明确使用 SDPA。UltraTex 自身的推理／注意力路径不由这个控件切换。

Windows／RTX 5090 Laptop 24GB／64GB RAM 上，原生 FlashAttention 2.8.3 已通过 FP16／BF16、head dimension 64／128、不等长序列的 CUDA packed 内核对照。下表是 BF16、8 头、head dimension 128，预热 3 次后同步计时 10 次的单次均值。

| Packed 负载 | 原生 | SDPA | 仅此内核样例的比值 |
|---|---:|---:|---:|
| 256 个等长序列，每个长 32 | 2.248 ms | 2.485 ms | 1.11× |
| 256 个不等长序列，长度 1–255 | 6.720 ms | 13.945 ms | 2.08× |

这不是整项任务提速。在同图、seed 0、512 分辨率、12 步、省显存、30 万面预算的完整几何对照中，**SDPA 为 359.211 秒，原生注意力为 505.729 秒**。原生运行记录了 1,260 次原生 packed 调用、0 次 packed SDPA 回退，说明扩展确实执行，但这次任务的总耗时仍更长。加载／PageIn 等开销影响了总时间，每种模式各一次也不足以形成普遍排名。两次输出有差异，不宣称逐字节等价。开发机原始记录：`data/uv-final-v045/attention.json`、`data/trellis-attention-v045/comparison.json`。

`data/uv-verified-v045/attention.json` 的同类算子复测得到不同耗时，尤其是不等长 SDPA。这种波动也说明应保留负载和原始记录，不宣传统一的加速倍数。

## 可选社区轮子

安装器支持固定的 [kingbri1 FlashAttention Windows 轮子](https://github.com/kingbri1/flash-attention/releases/tag/v2.8.3)，以及供上游可选 CPU 排布器使用的 [Numba 0.61.2](https://pypi.org/project/numba/0.61.2/)／[llvmlite 0.44.0](https://pypi.org/project/llvmlite/0.44.0/)。工件固定大小和 SHA256，验证后使用 `--no-deps` 本地安装，不替换 Torch、CUDA 或 NumPy。原生注意力要求已记录的 CPython 3.12／Windows x64／Torch 2.8.0+cu128 ABI；Numba 路径另要求 NumPy 1.26.4。

对兼容的完整包，先关闭工作台，再从包根目录执行：

```powershell
.\runtime\python.exe tools\setup_pipeline_runtime.py --runtime .\runtime-pipeline --attention-only
.\runtime\python.exe tools\setup_pipeline_runtime.py --runtime .\runtime-pipeline --uv-only
```

源码部署使用自身应用 Python，并将目标换成 `--runtime .pipelineenv`。完整环境安装时可用 `--skip-native-attention`、`--skip-uv-acceleration` 保留兼容路径。代码更新保留原环境，不会静默安装这些轮子。目标运行时中的 `attention-acceleration.json`、`uv-acceleration.json` 记录实际状态。安装／导入成功与 GPU 探针、首次 JIT、UV 正确性及性能测量分别验收；请以各项状态为准。可选 Numba 不可用时，保留上游 Torch 排布器并报告原因。

E 盘完整包已完成两组可选轮子的正式安装及 `pip check`。这证明安装与依赖一致性；导入回执不替代下方独立的 GPU／UV 验收。

## 模型目录

「模型与运行环境 → 模型目录」显示当前根目录与已保存配置。可设置绝对路径，或相对工作台根目录的路径；空闲时保存立即生效，无需重启。根目录内直接放置核心 `hi3d/`、`dino/`、`clip/` 与可选的 `extensions/`，可直接使用已有模型集合，无需复制进整合包。

任务、下载、校验、诊断或残留进程恢复期间禁止切换。程序不会移动或删除权重；目录不存在时，仅在下载需要时创建。「恢复默认」选回工作台下的 `models/`。代码更新保留 `config.local.json.models_dir`。选择另一个目录本身不证明存储瓶颈已消除，应比较实际加载耗时。

切换后，即使目录内已有核心文件，也需执行「重新完整校验」，通过后才显示就绪；存在权重文件不等于已完成安装验证。
